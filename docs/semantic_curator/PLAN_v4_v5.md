# AI 入坑 v4 / v5：以人物推薦為核心

更新：2026-10-26（台灣時間）。分支：`feature/curator-v4`。

## 1. 產品目標與範圍

AI 入坑要幫使用者找到「值得認識的成員」，並解釋這個人哪些特質符合偏好。v4 的主線是人物意圖、成員證據與有根據的推薦；歌曲曲風題占比不再決定開發優先序。

| 使用者需求 | 應使用的證據 |
| --- | --- |
| 喜歡某人的氣質，找相似人物 | 成員氣質描述、具名比較、公開感知的語境與不確定性 |
| 私下個性、互動或綜藝偏好 | 本人公開自述、訪談、公開節目中的具體行為，區分情境 |
| 舞台風格、表現力 | 指向成員本人的舞台／直拍／表演評述 |
| 聲線、唱法 | 成員本人的演唱、聲音描述與具名比較 |
| 平常與舞台的反差 | 兩面各自的證據，以及反差軸線；直接比較與工程推論分開 |

歌曲、舞台與影片可以是人物特質的證據，也可以是認識推薦成員的入口。團體歌曲的曲風、編曲不能直接推成成員個性或聲線；某人參加綜藝也不等於符合每一種搞笑方式。

**停止本次歌曲主線**：不再要求 25 團各 3–5 首、不補滿歌曲曲風／編曲配額、不擴大歌曲爬取、不建立歌曲索引來主導人物排序。既有歌曲資料、程式與稽核產物保留，不刪除、不當成本次部署依賴。獨立找歌功能若要發展，另立需求。

長相／造型相似與圖片向量仍不在本次範圍。歌曲清單與舞台片段不作成員人格的替代標籤。

## 3. v4 的實作順序（Codex 負責）

### A. 修正人物意圖與約束

沿用別名解析與同名消歧，輸出參照人物、目標面向、同團／其他團、正負條件與未解析狀態。沒有消歧成功不猜人；只有歧義確實影響推薦時才簡短澄清。沒有指定相似面向時保留綜合推薦，不能自動解讀為長相相似。

本人排除適用於「找相似／其他成員」，不是所有提到姓名的句子。團體硬排除只處理明確條件；同團探索保留同團候選。常用詞、暱稱、人名與曲名的字界／語境測試保留。

### B. 匯入成員證據，建立可回退的分面資料

先驗證 `grok_persona_v2.csv`、`claim_evidence.csv` 及後續成員修訂的 ID、field、value、來源主體、時間、scope、原文位置與支持狀態。全員盤點，先匯入可核實的子主張，不要求 154 位每欄填滿；不因少數缺漏阻塞整批，也不因有 URL 就整批通過。

保留既有 CSV，衍生資料進獨立版本目錄，每個主張帶 evidence_id 與來源雜湊。pending／unsupported／disputed 不進肯定理由；保留缺漏，未核可成員沿用 v3 檢索並明標證據限制。Grok 的明確比較、本人公開自述、節目行為與研究者推論分別儲存。

### C. 人物分面召回與約束排序

先用既有 v3 編碼器，分開處理氣質、公開私下互動、綜藝、舞台、聲線與反差；只對有證據的分面建索引，缺資料不能當成符合或相反特質。一般偏好保留綜合召回；明確條件以相應分面召回，再合併候選。來源類型與支持程度不假裝成校準過的機率。

反差需指定軸線：例如私下／舞台與外貌／個性不能互換。若沒有來源直接比較，但兩面均有可靠證據，工程可提出保守的「可能有這種落差」候選，標成工程推論，不得改寫成來源明說或交給資料 AI 補成 supported。先比較不使用推論的基線，再決定是否需要此選項。

先測 v3 → 修正意圖 → 加成員分面證據，拆開資料與排序效果；向量混合與多樣性只在人物開發資料選參。沒有合適的新證據則保留舊版本，不能靠換模型掩蓋缺漏。

### D. 推薦理由與入坑入口

Gemini 使用最終候選實際命中的證據，回傳理由與 evidence_id。不能把團體概念、泛用角色標籤當作個人成員的證據。程式驗證證據屬於該人／該面向；證據編號存在仍不代表文字忠實，需抽查是否過度延伸。

允許不足三位、部分符合、資料不足；本地 fallback 也必須遵守，不以泛用「反差萌」湊滿三個。每次推薦維持一次 Gemini 呼叫，API 失敗有本地退回。

優先附能展現命中特質的公開片段，沒有則保留已修好的同團 MV 入口並明確作一般入門用途；不得聲稱隨機 MV 證明個性。推薦、理由、追問、入口與上下文共用最終名單。

## 4. Grok 的新任務：成員證據整理

完整可轉交規格：`GROK_V4_MEMBER_TASK.md`。

優先整理已存在的 154 位成員與現有 claim，不重做長篇人格簡介；刪去或降級超出來源的形容，補上 evidence→人物→面向的明確對應。依全體資料缺漏與來源品質獨立選第一批約 12–20 位，涵蓋多團與不同面向，先交可驗證的小批，不為湊人數填空。

重用現有抓取／快取能力只為找到成員相關來源，不擴大爬網站或歌曲目錄。Grok 不看評估資料、demo、Bot 排名或理想答案；Codex 不把錯題的人名清單交給 Grok補標。

## 5. 評估改成回答人物問題

- real-dev 仍是工程選參來源，但先依問句目標獨立標記「人物／團體探索／歌曲作品／混合或不明」。定義先凍結，分類不看模型是否答對、不修改原題與原答案，不事後刪掉難題。
- 人物問題作主要報告；作品／找歌題保留為分開的相容性報告，不再靠歌曲總分選人物排序。只有 20 題有成員答案，分組後更少，必須報實際分母；若人物開發題不足，先補獨立的人物評估標註，不能只改報表就宣稱評估足夠。
- 新的人物開發／留出題由未參與資料研究的評估者獨立設計與標註，資料研究者不接觸；若尚未取得，明列限制，不宣稱盲測或泛化。主觀相似可接受多位合理候選並記錄分歧。來源關係表不能直接兼作自己的測試答案。
- 主指標：人物命中／適合程度、明確條件違反、本人回推、同團需求保留、推薦理由的證據忠實度、適當承認不足。跨團多樣性只在相應需求衡量，不能拿「不同團」當作推薦正確。
- 三個既有 demo 只驗證行為與剩餘限制，不拿來選參、補標或訓練。Grok 任務不引用這些題句、候選或預期人物。
- 正式 Codex 60 題、real-test、real-test-discovery 保持封存；完整方案與設定凍結後只驗收一次，同時報人物與作品分組、原始整體數字及實際分母，保留退步。分組規則須在開啟正式題前凍結，不為結果改分類。
- 與 v3 用相同資料／匯出流程的對照，報逐題勝敗與符號檢定；小樣本及五個百分點內差距不能當成穩定進步。文字理由另用固定輸出與人工檢查，不把 evidence_id 可解析誤當理由必然正確。

- **10/29**：決定 v5 是否值得做；未達人物品質與延遲條件則維持 v3／可驗證的 v4 部分。

- **10/31**：論壇分享，區分上線版本、開發結果與離線實驗。
